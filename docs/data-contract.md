# Generic data contract (core 0.5.3)

Native snapshots use schema `1.1`. Ask the running private Site for its contract: existing deployments may deliberately retain an older wire format through a private adapter. Never relabel or migrate stored data merely to install a core update.

- `spending.confirmedPlanningAssumptions` is optional. Its optional `recurringCosts` contains records with an ID, label, amount in cents, USD currency, cadence (weekly/monthly/quarterly/annual), evidence basis and estimate/confirmed status. Optional category/subcategory fields are identifiers chosen for that owner. Policy and workspace can independently hold these same records; an explicit workspace record supersedes a policy record with the same ID in the read model. Source observations never automatically approve a budget. Rules remain generic exact-ID, receipt, merchant, amount, date and split rules.
- `debt_payment` is a generic payment kind; full principal-plus-interest is not automatically economic spending. `excluded_discontinued` records historical costs that should not enter the ongoing baseline. Signed refunds still reduce actuals. Optional `discontinuedPayments` is a diagnostic amount, not a separate spend total.
- Declare source/workspace `classificationState: unclassified`, or configure `unclassifiedCategoryIds` in policy/workspace (policy takes precedence), to allow `unidentified_only` rules. No fixed shopping/other category identity establishes uncertainty. Explicit classified state wins over the configured list. Direct item corrections and exact receipt splits retain their existing priority.
- `portfolio.manualBalances` is optional. Each record has a stable ID, label, signed nullable value, currency, asset/liability kind, evidence basis, and status (`confirmed`, `documented`, `estimate`, `unverified`). Assets are nonnegative and liabilities nonpositive. No named property or liability type is mandatory.
- `portfolioReporting.netWorth` is optional. Its `manualBalanceIds` explicitly selects records; absence selects none. Net worth independently includes signed linked account balances. A selected estimate is permitted only as explicit owner policy; status remains in the reference evidence. Missing, unknown-valued or unverified selected evidence makes the total unknown rather than inventing a value. Unselected references never enter totals. A record referencing a linked account through `linkedAccountId` is already in linked scope and is not added again. Writers must identify duplicate evidence; never create two IDs for the same asset or debt.
Asset composition defaults to all evidenced positive linked assets plus selected manual assets, including a residence. Liabilities remain separate. Account balances and holdings count once; duplicate/manual references never add another asset. Unknown selected asset amounts make the complete composition unavailable. The center label and caption reflect the chosen scope.

Public examples are fictional. Build each owner's category labels, exclusions, asset families, captions and proposed targets from their evidence. Exports use the policy's exclusion reason or a generic fallback. The empty profile supplies no strategy targets, household assumptions or merchant rules.

Private legacy adapters may inject wire-schema validation, source-kind/category compatibility, classification diagnostics, portfolio input normalization and presentation helpers. They must preserve the original source/policy/workspace, use the shared arithmetic, and carry exact parity tests. A core release must not contain a recipient's adapter or private records. Review schema changes and adapters before adopting this breaking release; the hash-based updater does not perform data migrations.

## Required source inventory for new template imports

Native schema 1.1 remains readable without inventory for legacy compatibility. The new template's `write_finance_snapshot` requires `metadata.inventory`; existing private adapters keep their own writer contract. `verify_finance_setup` and `read_finance_effective_summary.inventoryVerification` reconcile persisted source and policy independently. Setup must not pass until verification `ok` is true.

`inventory.collectedAt` is the actual source collection instant, no later than snapshot `retrievedAt`. `collections` contains exactly `linked_accounts`, `manual_accounts`, `assets`, `liabilities`, each with `status` (complete/unavailable/not_authorized), `returnedCount` (exact count when complete, otherwise null), and `basis`. `expected` is captured from source responses **before** import selection; compare it to source totals, not just the derived imported array. Each record contains a unique pseudonymous `ref`, `collection`, verified underlying `entityId`, `kind` (asset/liability), `nature` (balance/alternative_valuation/redemption_claim), signed nullable `value`, USD `currency`, nullable `valuationDate` and `sourceAsOf`, `status` (confirmed/estimate/unverified), `basis` and `identityBasis`. Preserve source dates; collection time does not establish valuation freshness. Unavailable dates remain null.

Each expected reference has exactly one `dispositions` entry with `ref`, `disposition`, nullable `targetType` (linked_account/manual_balance), nullable `targetId`, and nonempty `reason`. An `included` balance must match its imported target's value/currency/date and, for manual records, kind/status/sourceAsOf/collectedAt. Its underlying entity and imported target can be included only once. Manual targets must appear in policy `portfolioReporting.netWorth.manualBalanceIds` before setup verification. This selection records authorized source inclusion, not an approved valuation or investment recommendation. A selected unverified/unknown amount still produces an unknown total.

`duplicate` and `alternative_valuation` entries point to the same included target and verified entity; they never add another balance. For example, a fictional manual equipment account and equipment asset record share one entity ID; an alternate appraisal is retained in inventory only. A manual debt and a liabilities record follow the same rule. Do not merge items just because their labels or values match. `unresolved` and `excluded` entries have null targets and explain why no balance is imported. A descriptive or undated redemption claim is not an added asset: leave it unresolved pending evidence, or exclude it explicitly when proceeds already reside in linked cash. A separately evidenced, dated receivable would require its own verified balance evidence and reconciliation against any received proceeds.

Every imported linked/manual balance needs one included disposition. Returned counts, duplicate refs, unknown targets, missing dispositions, duplicate inclusion and future dates fail validation. Missing manual net-worth selections fail setup verification. `coverageComplete` is false for unavailable or unresolved inventory, even if all records have an honest disposition. The ledger verifies the manifest supplied by the collector; it cannot discover a source record that a collector concealed from both the expected list and the returned count. Independently compare those counts with source responses on every setup/refresh.

## New-profile income-tax default

The empty profile opts into `incomeTaxDefaults` and provides unbudgeted Home and Income taxes categories. Optional transaction `taxAssessment` is `{kind: income|property|sales|ambiguous, confidence: high|unknown, basis: nonempty evidence}`. Only high-confidence income-tax evidence receives default income-tax exclusion. Assess **personal income tax** using verified tax-agency identity, the payment/refund description and personal-versus-business account context together. The literal words “income tax” are not required when this combined evidence establishes the purpose. Agency identity, amount or generic category confidence alone is insufficient; agency payments can also involve business taxes, property tax, penalties or other liabilities. Record the supporting facts and confidence in `taxAssessment.basis`; preserve source classifications and the original signed refund amount. If uncertainty remains, keep it ambiguous and group related payments into one concise clarification, referencing all relevant `sourceKeys`; do not ask the same question transaction by transaction. Prefer `tax-type` or `tax-type:<group>` clarification IDs. A saved tax-purpose question covering the same source key suppresses the generic duplicate while retaining unrelated questions and the source uncertainty. Canonical tax-type IDs carry purpose intent; legacy text matches only a direct tax-type/purpose question or an explicit list of tax-purpose alternatives. Date, duplicate-payment, receipt and refund-destination questions do not resolve tax purpose, even when the saved question is resolved. This is a reporting convention, not tax or legal planning advice. Property tax maps to Home, sales tax stays with its purchase, and ambiguous/low-confidence tax evidence is included when it is a spending payment and generates a To clarify question. Keep uncertain transaction membership separate; do not call an unidentified transfer spending merely because its payee is a government.

Policy `incomeTaxTreatment` can be `exclude` or `include`; absence means exclude only on profiles that explicitly opt into the new default. Excluded income-tax payments and signed refunds remain visible in Transactions/CSV; they contribute neither spending actuals nor budget totals. Item categories, exact receipt splits and existing explicit exclusion policies retain precedence. Resolving an ambiguity in chat should save the actual category/tax evidence (or a resolved clarification), not simply mark an unknown payment as reviewed. Core upgrades do not replace profiles, add the default to an existing owner, or rewrite old policies.

## Amount evidence, freshness and metric availability

Manual status `documented` means the amount has identifiable document evidence, without claiming owner confirmation, current valuation or independent bank verification. Keep absent `valuationDate` and `sourceAsOf` null; collection/record-update timestamps are not valuation dates. Record the evidence in `basis` and use the same status/value/dates in the inventory. `estimate` remains approximate and `unverified` stays unavailable for totals. The code never promotes a record by parsing its description.

`metricAvailability` reports completeness, known subtotal and missing-component count separately for assets, liabilities, net worth and liquid net worth. Incomplete subtotals are never complete totals. Unknown assets do not erase known liabilities; unknown retirement/manual assets excluded from liquidity do not erase eligible liquid assets. Missing selected manual records have unknown kind. Canonical account balances define totals: known holdings cannot replace unknown balances and negative holdings reconciliation is not debt. Explicit zero investments plus an empty holdings list allows cash-only allocation.

With an empty `profile.familyClasses`, group recognized taxonomy subclasses under **Equity**, **Credit / debt**, **Real assets** and **Cash**. Mixed asset funds retain a separate family without invented look-through. U.S. and international equities share Equity; government bonds and corporate credit share Credit / debt. Optional taxonomy `familyId` selects a standard family (`equity`, `debt`, `real_assets`, `cash`, `mixed_multi_asset`, `unclassified`). A justified additional family uses `portfolioReporting.families: [{id, label, basis}]` plus each child's `familyId`. Unrecognized or conflicting class labels (such as Infrastructure equities) keep their value in an explicitly unresolved family until assigned; an explicit familyId takes precedence over keywords. Existing explicit profile mappings take precedence and are never rewritten.

Both pie rings use the same selected positive-asset denominator; the inner ring retains subclasses, while the outer ring and composition table sum their siblings. Every child belongs exactly once. Parent dollars, percentages and targets must reconcile to children, with any unknown child target making its parent target unknown. Generic presentation shows unknown targets as —; a pre-existing profile's explicit unassigned-family presentation remains compatible. Setup verification also checks each resolved parent identity and rejects split recognizable broad siblings in inferred defaults and unjustified unresolved families. Explicit policy familyId assignments and existing owner mappings may intentionally split siblings: merely counting membership or avoiding Unclassified is insufficient. Cash-only portfolios and legitimate one-child families are valid. Never infer instrument exposures from a name or change owner targets to fit the chart.

## Composition and target scope

The generic default is `all_assets`: all evidenced positive linked assets and selected eligible manual assets, including a residence. Negative liabilities are separate from composition. Evidenced positive credit/loan account balances are receivable assets and appear once under Credit / debt by default, with their own labeled subclass and unknown target; an explicit balance classification still takes precedence. A residence already included through a linked account is not added again. Unknown selected assets make composition unavailable, not a smaller apparently complete pie. Explicit `portfolioReporting.composition: {scope: "investments_and_cash", basis: "Owner's chosen allocation scope"}` selects an investment-only chart. A private profile may preserve a standing scope through `compositionScope`; this overrides the generic policy/default. Do not copy another owner's home exclusion into a new profile.

A selected manual/other linked asset is a distinct subclass by default; clear residence/property labels group under Real assets. For an evidenced taxonomy assignment use `balanceClassifications: [{source: "manual"|"linked", balanceId, assetClassId, basis}]`. No asset value is dropped merely because its family is unresolved. Prefer explicit assignments for ambiguous labels. A selected amount must be eligible (`confirmed`, `documented`, or `estimate`), with original dates/status preserved.

Set `targetProvenance.compositionScope` to the actual saved target scope (`all_assets` or `investments_and_cash`). **Actual vs. Target** uses that scope independently of **Composition**, with a visible scope label when they differ. Its actual percentages, target dollar amounts, differences and tooltips all use its own denominator. All-assets Composition keeps the selected residence; investment-only comparison omits it, without inventing a residence target or changing any saved weight. Targets remain unknown in a composition table whose scope differs. `portfolio.targetComparison` exposes the separately reconciled projection; `PortfolioModel.comparison(pf)` returns its display model. Setup accepts two valid independently reconciled scopes. Missing/invalid target scope remains unresolved and hides comparisons, with a needed-choice message. A private profile can preserve its documented target scope via `compositionTargetScope`. No source/policy migration or normalization is performed.

## Proposed budget comparison scope

Every active proposal needs `comparisonScope: {excludeUnresolvedTaxes: boolean, excludedSourceKeys: string[], basis: string}`. Use exact native transaction IDs for identified one-time costs or other evidence-based proposal exclusions; use an empty array if none. Set `excludeUnresolvedTaxes` to match the estimation basis, not to reclassify the payments. Merchant identity, size and generic tax-category confidence alone do not establish income-tax type. Preserve explicit property tax in Home and sales tax in its purchase.

The budget table and subcategory variance use the declared scope and disclose omitted signed totals/counts. Full spending remains unchanged in the headline, chart and Transactions. Chart budget overlays are hidden when the scopes differ. Approved budgets do not inherit a stale proposal scope; approval and any confirmed spending exclusions are separate owner decisions. `verify_finance_setup` checks scope/reconciliation, family coverage, independent metric availability and amount evidence/freshness in addition to inventory. Warnings about truthful unknowns do not imply setup failure.

## Same-collection corrections (template contract 5)

`metadata.retrievedAt` is the actual collection instant, never a convenient snapshot assembly/version timestamp. A justified interpretation or transcription correction uses the existing `write_finance_snapshot` tool with an explicit `correction` option:

```js
{
  expectedRevision: current.revision,
  snapshot: correctedSnapshot,
  correction: {
    expectedDigest: current.digest,
    correctedAt: actualCorrectionInstant,
    reason: "Evidence supporting the correction; original source dates retained."
  }
}
```

Read current state first. Preserve the collection/provider dates, freshness and record scope exactly. Change only the justified evidence fields and matching inventory fields. The writer validates inventory, requires revision and digest preconditions, archives the previous payload by digest, and adds `metadata.correction` containing this option plus `baseRevision`. This audit is part of the resulting canonical snapshot digest. The timestamp-derived snapshot ID still names the collection; the revision and digest identify a particular corrected version. Reuse the exact request, including `correctedAt`, for an uncertain retry; identical resulting content is idempotent. A stale base or concurrent change fails. Read back and compare against the submitted snapshot plus server-added provenance, then verify effective results and unchanged policy/workspace.

This narrow correction path does not add/remove records, change source dates or claim a new query. A genuinely new query uses the ordinary refresh path with its real collection timestamp and omits prior `metadata.correction`. Previous corrections remain in archived history. Restore through the existing snapshot restore route using an archived digest and current revision; restoration also preserves original source dates. Never patch a private writer or freshen timestamps to avoid a conflict.
