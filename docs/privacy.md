# Architecture and privacy

Each owner gets a separate private Site and D1 database. `finance_snapshots` stores the current native source snapshot and refresh history; `finance_reporting_policies` stores versioned owner policy; `spending_workspaces` stores the signed-in owner's independent categories, rules, item edits and splits. Snapshot writes use optimistic concurrency and an identical-content digest check. Policy writes and workspace writes are separate operations. Routine source refresh does not replace either.

The public template has no connection to Finances. The owner's dot queries its own authorized connector and writes a minimized native snapshot through that owner's private Site plugin. The Site MCP requires the signed-in Sites identity for tool calls; the hosting platform supplies and validates that identity. HTTP source/policy routes additionally rely on the owner-private hosting boundary. Site-wide source and policy storage is intentional for a one-owner deployment and is **not tenant isolation**. Do not deploy the backend publicly, grant additional viewers, trust client-spoofed identity headers, or place it behind an unrelated host without redesigning authorization and storage.

No secret, financial record, owner identifier, provider ID, linked-account mask, private policy, deployment identity or personalized profile belongs in this repository. The fixtures are synthetic. Keep the public clone pristine and personal configuration in a separate private deployment. Local preview authentication is synthetic and is never an authorization test. Ignore rules are defense in depth, not a substitute for reviewing every file before a public commit.

The shared core renders data without mutating the source. Unknown amounts and coverage stay unknown. The profile provides presentation settings; application-specific rules remain private. The template starts with no portfolio target. Onboarding may populate clearly labeled suggestions using explicit provisional assumptions; private provenance distinguishes them from owner-approved targets. Do not conflate an institution's source timestamp, the time the dot collected a record and the time the Site stored it.

The snapshot schema retains posted transaction-level detail for filtering and preservation of user edits. This is more sensitive than aggregate-only data; the setup request must authorize these records to the private destination. If the owner wants aggregates only, do not import rows into this template: explain the limitation and adapt the UI/schema first.

Third-party build support retains its bundled license notice. This repository does not change any upstream dependency license or grant access to OpenAI services. Account eligibility, connector permissions and deployment privacy must be checked per recipient.
